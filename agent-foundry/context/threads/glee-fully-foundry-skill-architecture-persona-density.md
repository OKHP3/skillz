## Decisions and rationale

1. **Treat GPT building as product engineering.** A reusable assistant must outperform a one-off prompt and have explicit purpose, scope, failure modes, and acceptance criteria.
2. **Use a repo-backed source of truth.** UI configuration is useful for deployment but is not sufficient for auditability, diffing, portability, or long-term maintenance.
3. **Make the method bidirectional.** The same architecture should build a new assistant from a product brief and reverse-engineer an existing assistant into a product brief and skill package.
4. **Keep the method cross-platform.** Custom GPT, Gemini Gem, and Copilot Agent are deployment surfaces with different current capabilities; shared behavioral logic should be separated from platform adapters.
5. **Use progressive disclosure.** Put operational contract and routing in `SKILL.md`; place durable detail in references, examples, scripts, and evals rather than creating one unmaintainable instruction blob.
6. **Use overlays instead of forks when possible.** A shared core can support different audiences and brands through `references/repo-overlay.md` or an equivalent adapter layer.
7. **Verify volatile claims.** Platform limits, pricing, tool compatibility, model behavior, and publishing rules must be checked against current primary documentation before being presented as definitive.
8. **Require evals and red-team coverage.** Happy paths alone are insufficient; ambiguity, tool choice, retrieval, out-of-scope requests, injection, privacy, refusal/deferral, and publishing behavior need explicit tests.
9. **Preserve a manifest.** A manifest records package purpose, version, license, authority by file, inventory, verification rules, and maintenance posture so future agents do not have to rediscover the package structure.
10. **Test round-trip fidelity.** Rebuild or reconfigure the user-facing assistant from the portable package and compare the resulting behavior with the source assistant; document semantic loss rather than assuming equivalence.
11. **Route Notion first, GitHub second.** The capture page and extract rows preserve provenance and reusable value; existing repositories hold versioned implementation. No new repository should be fabricated from a capture.
12. **Separate verified facts from historical claims.** The current artifact can verify the existence of a Notion capture and listed repository destinations, but it cannot independently validate the inaccessible Claude transcript or every historical implementation detail.
13. **Scope forge personas explicitly.** ForgeDialect.A1 (craftsman) and Watchkeeper.Core (governor) are internal operating voices for the FoundRy. They must not leak into the skills or Tools produced by the forge unless a downstream artifact explicitly defines a separate, authorized persona.
14. **Replace constraint-era tone labels with Persona Density.** Full, Standard, Lean, and None describe deliberate UX and role-fit choices. They are not a workaround for an obsolete instruction-character budget.
15. **Make Twig audience fit explicit.** A required “Best for” section should state the triggering user state, intended audience, and gentle disqualifiers before core behaviors.
16. **Use zero-personality guardrails at execution leaves.** Function and Function-ette packages should prioritize exact logic and scope discipline over character or narrative overhead.

### Persona Density and hierarchy standard

Use the five-level hierarchy `Trunk > Branch > Twig > Function (Leaf) > Function-ette (Falling Leaf)` to set expectations for scope and narrative weight. Persona Density is a separate parameter: Full for ecosystem-facing experiences, Standard for ordinary tools, Lean for narrow or utility-oriented tools, and None for pure execution leaves. The density choice should be justified by user experience and role, not by a legacy character limit. ForgeDialect.A1 and Watchkeeper.Core remain forge-internal operating voices; a produced Tool should not inherit them automatically.

### Twig format standard derived from Neighborly Bazaar

Require a “Best for” section between Role & Scope and Core Behaviors. It should describe the user state that triggers the tool, the audience it serves, and the situations where another tool is a better fit. Pair it with explicit Inputs & Outputs, a complete sibling list, and surgically scoped Functions. Treat this as a guardrail and routing aid, not promotional copy.

### PromptChain translation

Map PROMPT00–PROMPT05 into skills-era authoring stages: intake and canon, architecture, knowledge/reference routing, behavior and output contract, evaluation and red-team design, then release sealing and repository validation.
