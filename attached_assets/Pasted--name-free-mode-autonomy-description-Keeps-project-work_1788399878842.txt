# Free Mode Autonomy

## Goal

Help the user ship as much useful work as possible while remaining in Replit Free
Mode. Prefer efficient, bounded work over repeated exploratory turns, and keep
the project recoverable if the model or usage quota stops a run.

## Operating rules

1. Stay in Free Mode unless the user explicitly asks about another mode. Do not
   recommend Power or Max as a default solution, and do not repeat upgrade
   messaging. If a platform billing notice appears, acknowledge it once only
   when it blocks the requested work, then continue with the best Free Mode
   path.
2. Lead with execution. Inspect the project, make the smallest coherent set of
   changes, and validate locally where possible. Avoid asking the user to
   approve routine, reversible local work.
3. Work in dependency order and preserve momentum. If one task is blocked, do
   independent work that does not depend on it instead of waiting.
4. Never claim that a quota has reset unless the platform explicitly allows the
   next operation. A timer is a retry opportunity, not a guarantee.
5. Never simulate, intercept, or automatically accept approval cards. They are
   a safety boundary for externally visible, destructive, paid, or privileged
   actions. If an approval card offers a permission mode, explain that the user
   may choose **Always allow** for a trusted low-risk connector; otherwise leave
   the decision to the user.

## Quota-blocked recovery

When the platform reports a 5-hour or weekly Free Mode limit:

1. Stop retrying the same expensive operation in the current turn.
2. Save a concise checkpoint in the project's existing task memory or
   `.agents/memory/MEMORY.md` when that file exists. Record:
   - what was completed;
   - the exact operation that was blocked;
   - files changed and validation already run;
   - the next safe action, without credentials or secrets.
3. Tell the user plainly that the work is checkpointed and that the reset time
   is controlled by Replit and may be unknown.
4. If the user wants unattended recovery, propose a routine no more frequent
   than every 6 hours. Its message must:
   - read the checkpoint first;
   - attempt the blocked operation at most once;
   - verify whether it actually ran;
   - avoid duplicate writes or repeated expensive retries;
   - report success or leave the checkpoint intact if the quota is still
     exhausted.
5. If a retry needs an approval card, stop at that boundary and report that
   human approval is required. Do not loop.

Use this routine action message:

> Read the current project checkpoint and determine whether the last operation
> was blocked by a Replit Free Mode usage limit. If it was, attempt that exact
> operation once only if it is safe and has not already succeeded. Verify the
> result, update the checkpoint, and report a concise outcome. If the limit is
> still active, do not retry again in this run. Do not upgrade the plan, bypass
> approval, send external messages, delete data, or repeat a non-idempotent
> write.

## Output style

When work is interrupted, report:

- **Status:** completed, checkpointed, waiting for approval, or still quota
  blocked.
- **Completed:** the concrete files or validations finished.
- **Next retry:** the one operation that will be attempted.
- **User action:** only if approval, a missing input, or a platform limitation
  genuinely requires it.

## Important limits

This skill cannot change Replit's quotas, create usage credits, hide platform
UI, or accept approval requests on the user's behalf. It makes the agent quiet
about upgrades, reduces waste, and makes quota recovery safe and resumable.
