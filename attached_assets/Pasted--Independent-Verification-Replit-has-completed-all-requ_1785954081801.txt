## What's still broken, confirmed live, right now

**1. Per-skill provenance is fabricated in production.**

I fetched `https://okhp3.github.io/skillz/data/catalog.json` directly and sampled skills across families. Every one carries identical values:

```
createdAt:    2026-08-04T18:33:01Z
lastModified: 2026-08-04T18:33:01Z
commitSha:    98515ec5
```

That's the deployment timestamp and a single commit SHA, not real git history. This isn't cosmetic. It's the app claiming to know when a skill was created and last touched, and being wrong for all 113 entries. Root cause per the Replit docs: the Pages build checkout is shallow, so `git log --follow` per-file lookups silently fail and fall back to deploy-time. Not fixed.

**2. The public dossier (overkillhill.com) is stale and now actively misleading.**

I fetched `https://overkillhill.com/projects/skillz/` directly. It still says:

> "75 public distribution skills across 12 active families. Source-derived count from the July 29, 2026 skill maturity audit."

Actual: 113 skills, 15 families. That's an 8-day-old snapshot presented as current.

Worse: it labels **Compare** and **live GitHub Activity** as "Planned," when the capability audit (and my own earlier review) confirms both are live in Forge right now. The dossier isn't just outdated on a number. It's underselling shipped functionality to anyone who lands on it from outside the repo, which is exactly the audience a "distribution center" exists to serve.

**3. No release tag exists.** `git tag -l` on your local mirror returns nothing. Confirms the capability audit's claim directly.

## A governance problem worth naming

There are now four documents dated 2026-08-04 claiming authority over this project's next steps: my PRD, and three Replit-authored artifacts (`PRD-SKILLZ-FORGE-EXECUTION-RESET`, `PRD-SKILLZ-FORGE-INDEPENDENT-COMPLETION`, and the capability-maturity audit). `EXECUTION-RESET` explicitly claims to reconcile and supersede the other two.

Worth sitting with: Replit is now auditing its own work and writing its own next directive. To its credit, the audit is unflinching. It correctly flags both P0 items I independently confirmed above, so it's not whitewashing. But letting the implementing agent set its own next agenda is a structural conflict of interest, and you're about to sink another large token budget into a session working from whichever of four documents it decides to prioritize. That's not a knock on the content, it's a process risk.

## Recommendation

Don't kick off the next Replit session against any of the four existing documents as-is. Issue one reconciled directive, scoped to exactly two things:

1. Fix live per-skill provenance (full-history checkout in the Pages workflow, fail the build if provenance can't be established, no silent fallback to deploy-time).
2. Make the public dossier consume the same generated source-of-truth the app uses, so it can't drift again, and commit + push + propagate the `PUBLIC_SURFACES.md` fix that's already sitting locally.

Everything else in the three self-authored docs (contract inspection in-app, evidence semantic cleanup, stack composer) is real and worth doing, but it's P1/P2. Don't let it dilute the session against the two things that are currently making the public-facing product say false things about itself.
