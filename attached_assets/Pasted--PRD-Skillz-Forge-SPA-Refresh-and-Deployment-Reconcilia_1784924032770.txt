# PRD: Skillz Forge SPA Refresh and Deployment Reconciliation for Replit

## Directive status

This is the implementation directive for the Replit project at <https://replit.com/t/overkill-hill/repls/skillz>. It authorizes a focused, production-quality refresh of the existing Skillz Forge application in `OKHP3/skillz`. It is not authorization to create a replacement landing page, a second catalog, a generic AI marketplace, or a disconnected Replit demo.

The public application is <https://okhp3.github.io/skillz/>. The canonical project narrative is <https://overkillhill.com/projects/skillz/>. GitHub at <https://github.com/OKHP3/skillz> is authoritative for installable files, repository history, issues, pull requests, and reviews.

This directive supersedes earlier SPA handoffs when they conflict with the current repository, generated catalog, or public deployment.

## Observed baseline and non-negotiable synchronization gate

The repository changed materially on July 24, 2026. At the time this directive was prepared, the canonical catalog declared **68 public distribution skills across 11 active families**, while the visible Replit preview still presented **67 skills**. The Replit Git pane also showed a divergent local branch with a rejected push. Treat the preview as stale until proven otherwise.

Before editing product code, Replit must:

1. Inspect the deployed SPA at `https://okhp3.github.io/skillz/`, the local Replit preview, the checked-out Replit commit, and `origin/main`.
2. Record the checked-out commit, upstream `main` commit, working-tree status, and generated catalog metadata.
3. Reconcile the Replit checkout with the repository using a safe, reviewable Git workflow. Do not discard unreviewed work, remove lock files, force-push, or use a destructive reset to make the warning disappear.
4. Resolve conflicts deliberately. Preserve repository changes that belong to the current upstream state and isolate any independent Replit work for review.
5. Regenerate the Forge catalog from the reconciled repository state. Do not preserve a hand-edited count, stale timestamp, stale source commit, renamed package identifier, or retired family composition.

The implementation may begin only after the local catalog, the application data it imports, and the current repository tree agree. If Git reconciliation requires a user decision, stop and report the exact conflict rather than guessing.

## Product definition

Skillz Forge is the flagship public discovery workbench for reusable Agent Skills in the OverKill Hill P³™ ecosystem. A visitor should be able to begin with a real outcome, find an appropriate `SKILL.md` delegation contract, understand its operating boundaries, inspect its source, and move into GitHub when ready to install or contribute.

It is a readable, generated view over the repository. It is not the source of truth, an authenticated agent runtime, a marketplace, a social feed, or a promise that every skill is production-ready.

The public-surface division is intentional:

| Surface | Job |
|---|---|
| GitHub `OKHP3/skillz` | Source, version history, installable directories, issues, pull requests, review, and contribution. |
| Skillz Forge SPA | Fast task-oriented discovery, inspection, comparison, curated composition, sharing, and routing into GitHub. |
| OverKill Hill `/projects/skillz/` | Flagship project dossier, ecosystem explanation, credibility, and route into the app and repository. |

The SPA and the project page must feel like one designed system with different jobs. Neither may imitate or duplicate the other.

## Primary outcome

Deliver a current, fast, accessible, visually distinctive Skillz Forge at `https://okhp3.github.io/skillz/` whose catalog demonstrably matches the reconciled repository and whose presentation makes the library feel useful on the first visit.

Success is not a more decorative home screen. Success means a person can answer these questions quickly and accurately:

1. What is an Agent Skill and why does `SKILL.md` matter?
2. Which skill or stack helps with the work I need to do?
3. What is the scope, maturity, safety posture, and companion context of that skill?
4. How do I inspect, copy, install, share, or contribute to it without leaving the source of truth ambiguous?

## Required experience

### 1. Home and task-first discovery

Retain and improve the task-first entry point. The opening view must communicate the purpose in one glance and invite a real search, not a category guess.

Required behavior:

- Prominent, keyboard-ready natural-language search with useful example prompts tied to actual skills.
- A clear route to browse all generated public skills using the actual count.
- Visible family and stack entry points that do not require the visitor to understand the repository layout first.
- A concise explanation that the catalog is generated from GitHub source and links to the canonical project page for the broader thesis.
- Empty, loading, error, and no-results states that offer recovery paths rather than dead ends.

Do not hard-code the public count in a component. Read it from the same generated data that powers search and family navigation. The UI must make it difficult for a source update to leave one visible total, family card, result count, metadata block, or share label behind.

### 2. Explore and filtering

The browse surface must make the 11 active families intelligible without exposing placeholder or project-local infrastructure as public inventory.

Required controls:

- Family filter.
- Maturity filter when the generated source supplies maturity.
- Search that covers the user-facing name, description, triggers, tags, family, and practical examples.
- Stable URL state for search and filters where the current routing architecture supports it.
- A clear reset action and an accessible result summary.

Use graceful degradation for metadata that is absent or inconsistent. Never invent a maturity label, runtime support claim, version, installation path, or validation state.

### 3. Skill detail routes

Every generated public skill must have a stable, directly shareable detail route. A detail page must present the current data without manufacturing content that is not in the source contract.

Include, when available from generated data:

- Display name, canonical package name, family, summary, and maturity signal.
- When to use it, trigger language, intended outcome, and important boundaries.
- Companion or prerequisite skills, including ordering rules where source declares them.
- Practical examples or stack membership.
- Direct GitHub source and raw-file links that resolve to the correct package.
- Copyable installation or acquisition guidance that clearly distinguishes a copied directory from a package-manager installation.
- A safe, native GitHub contribution path.

For missing fields, show less rather than plausible filler. A missing example is not permission to write one in the catalog as if it came from the package.

### 4. Curated stacks and composition

Keep the existing stack model and update every reference after the repository reconciliation. The currently supported curated pathways include:

- Governed Mermaid Workflow.
- Process Documentation Pipeline.
- LinkedIn Content Pipeline.
- New Skill Creation Pipeline.
- AI Conversation Capture and Reconciliation.

For each stack, show the problem, intended audience, ordered steps, inputs and outputs where sourced, optional steps, and direct links to each constituent skill. Validate every referenced package against the generated catalog. A stack must fail a build-time integrity check if it references a deleted or renamed skill.

The process documentation stack must reflect the current package names, including `okhp3-process-gap-analysis`, `okhp3-process-controls-metrics`, `okhp3-sop-work-instructions`, `okhp3-process-quality-validation`, and `okhp3-handoff-packaging` where applicable. The context-extraction stack must use the renamed platform adapters from current source.

### 5. Compare, favorites, sharing, activity, FAQ, and contribution

Retain real shipped functionality and make its limits explicit.

- Compare two to four skills with a useful accessible comparison layout.
- Store favorites only in browser-local storage and describe that accurately.
- Preserve stable share URLs and copy/share controls.
- Identify activity as a static generated catalog snapshot unless it actually reads live GitHub data.
- Preserve the FAQ and contribution routes, ensuring they agree with the repository’s public contribution model.
- Link to GitHub for issues, pull requests, discussions, and security-sensitive reporting. Do not simulate GitHub actions inside the SPA.

Do not claim live repository polling, authenticated comments, pull-request collaboration, custom cloud accounts, or hosted agent execution unless those features are actually implemented and tested.

## Visual and content direction

Skillz Forge should feel like a precise public workbench, not a startup template or an enterprise dashboard. It belongs to OverKill Hill P³™ while retaining a distinct product identity.

Use the existing Forge design system and preserve good current work. Improve hierarchy, density, responsive rhythm, and information clarity where evidence supports it.

Required character:

- Warm paper, ink, dark espresso, rust, ochre, olive, and controlled teal accents.
- Editorial headings paired with legible body copy and technical metadata styling.
- A tool-like sense of inspectability: source cues, provenance, purposeful dividers, and structured data.
- Clear contrast and recognizable focus states in light, dark, and system color modes.
- Motion only when it improves orientation, with reduced-motion support.

Avoid generic AI neon, purple-gradient SaaS styling, excessive pills, huge decorative dashboards, meaningless badges, fake utilization statistics, pricing, testimonials, or a visual clone of the parent website. Do not add em dashes to new copy.

The current narrow Replit preview is not representative responsive QA. Test the complete app at 1440px, 1024px, 768px, and 390px, plus keyboard-only navigation and at least one screen-reader-oriented semantic pass. Ensure headings, search, result cards, filters, compare view, stack steps, and CTAs remain usable without horizontal scrolling.

## Technical implementation rules

Work in the existing Forge application under `forge/`; do not introduce a second frontend or manually maintained catalog.

Required repository contract:

1. Treat `SKILL.md` packages and generated catalog inputs as source data.
2. Use the repository’s existing catalog-generation path and update it when needed so it consumes the current public distribution surface only.
3. Keep `forge/src/data/catalog.json`, `.catalog-meta.json`, `skillz.manifest.json`, root catalog surfaces, and app-visible counts consistent with the reconciled source.
4. Preserve the deployed GitHub Pages base path and routing behavior. Deep links and refreshes must resolve on the live site.
5. Keep the app build static and avoid runtime dependencies on unauthenticated GitHub APIs for core discovery.
6. Keep analytics privacy-preserving. Never transmit raw search phrases, copied skill content, credentials, personal information, or repository-private data.
7. Use only repository-safe public examples. Exclude employer-specific material, secrets, tokens, cookies, and hidden network calls.

If a catalog-building or deployment script needs correction, make it deterministic and document the source-of-truth rule. Do not paper over a mismatch by editing only generated output.

## Data integrity acceptance gates

The following gates are mandatory before deployment:

| Gate | Required evidence |
|---|---|
| Upstream alignment | Current `origin/main` commit, working-tree state, and reconciliation decision recorded. |
| Inventory | Generated public skill count equals the catalog count displayed by the app. |
| Family coverage | Exactly the generated active families appear in browse controls; placeholders and `.agents/skills/` do not appear as public families. |
| Link integrity | Every skill detail, raw file link, GitHub source link, companion link, and stack reference resolves to the current package path. |
| Provenance | Generated timestamp and source commit are current or transparently described as the precise source snapshot. |
| Route integrity | Home, explore, detail, stacks, compare, FAQ, activity, and contribute routes work through direct navigation and refresh in the GitHub Pages deployment. |
| Content truth | No feature, count, maturity, compatibility, or workflow is claimed without source evidence. |

Run the repository-supported catalog and structural checks, then the Forge build and relevant tests. If known repository-wide test failures are unrelated name assertions, record them precisely and do not reinterpret them as a successful verification of unrelated work.
